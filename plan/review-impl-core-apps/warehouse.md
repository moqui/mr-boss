## Questions for the user

1. **Warehouse admin scope.** P1 says BOSS_WAREHOUSE_ADMIN works in every facility of every organization until one is active (impl-drawers-commons §4). Products as built scopes every non-framework-ADMIN user by membership (`get#CatalogOwnerScope`), and its WarehousePolicy guard does not admit the Warehouse admin. *Recommendation:* follow the shared rule. Make one owner-scope helper honour it for each app's admin group, and fix Products' helper with it, so that Warehouse P1 and P3 agree with the code.
2. **Where the capability check sits** (I-WH-08). *Recommendation:* use thin `ironstone.warehouse` services that call AccessServices, then the Mantle entry point. Mantle names no BOSS group, so move Products P7's group checks out of `WarehousePolicy.js`. The other choice is a neutral capability check inside Mantle, which no other plan uses.
3. **The BOSS demo organization** (I-WH-07). *Recommendation:* make a new internal organization outside ORG_ZIZI_CORP's rollup, with its own warehouse and accounting setup and the Accounting and Warehouse flags on, shared by Accounting's, Warehouse's and Manufacturing's demos. ORG_ZIZI_RETAIL and ZIRET_WH stay as Mantle's specs expect them.
4. **The negative-stock policy** (I-WH-05). *Recommendation:* BOSS guards never issue past on-hand, whatever `assetAllowIssueOverQoh` says. ZIRET_WH keeps Y for Mantle's specs, and FacilityDetail shows the flag read only.
5. **A reorder read before CX-PLANNING.** Products P7 lets a planner set minimum, maximum, reorder quantity and method, but nothing reads them until Manufacturing P13, so a standalone Warehouse organization gets no reorder signal. *Recommendation:* a "Below reorder point" list in P17, over ProductFacility levels and `get#AvailableInventory` (S), as Odoo's replenishment report reads its orderpoints (`3p_other/odoo/odoo/addons/stock/models/stock_orderpoint.py`). Suggestions and conversion stay with CX-PLANNING.
