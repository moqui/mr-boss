# IronStone BOSS — Customer Service design

Nov 1, 2026 — draft; reviewed against research-customer-service.md, the reference apps and the other core designs ([review-core-apps.md](review-core-apps.md)); saved replies are Comms text blocks, case rules run from Request ECA rules, returns split into authorize, label, receive and settle, order changes narrow to cancellation and short-pick substitution, and three screens take full-word names; then brought in line with [impl-customer-service.md](impl-customer-service.md) §4 and the shared rules of [impl-drawers-commons.md](impl-drawers-commons.md) §4: a case's organization and people as RequestParty roles, effective-dated policies and settings, a case as a request in a service queue, order changes, warranty claims and case templates on Request and DbForm, the Mantle case core, the §14 items decided, and the customer pages as the PASS app Support; consistency pass: brought in line with the Accounting and Warehouse builds and the Nov 1 decisions

This design is for support agents, order-desk staff, service managers and customer contacts. It covers case intake through resolution, order enquiries and controlled changes, customer returns, warranty coordination, knowledge and feedback. It specifies screens and proposed extensions; it does not implement them. A business can use Customer Service on its own by granting the required business capabilities to its staff.

Inputs: [research-customer-service.md](research-customer-service.md), [design-doc-guide.md](design-doc-guide.md), [ss-inventory.md](ss-inventory.md), [usl-inventory.md](usl-inventory.md), [style-guide.md](style-guide.md), [initial-design.md](initial-design.md), [design-crosscut.md](design-crosscut.md), [Commons](design-drawers-commons.md), [Projects §6](design-projects.md#6-requests), [Products](design-products.md), [Warehouse](design-warehouse.md) and [Accounting](design-accounting.md); the decisions of [impl-customer-service.md](impl-customer-service.md) §4 and [impl-accounting.md](impl-accounting.md) §4. ## 1. Shell

Existing root scaffold `CustomerService`, title **Customer Service**, icon `sym_o_support_agent`; its `BOSS_CUSTOMER_SERVICE` artifact group and the admin authz (`ADMIN` and `BOSS_CUSTOMER_SERVICE_ADMIN`) are live, and the root user group and the ordinary groups come with the implemented screens. `BOSS_CUSTOMER_SERVICE` is both the root user group and the root's artifact group; global saved replies are shared with their organization's service agents group `SVO_<organization>`, not the root user group, which spans organizations (§9 SavedReplies). The app's groups take the `MANTLE_USER_ORG` and `MANTLE_PRIVATE_CONTACT` filter sets, and `BOSS_CUSTOMER_SERVICE_ADMIN` has all authz on the root with `MANTLE_ACTIVE_ORG` and `MANTLE_PRIVATE_CONTACT` (impl-drawers-commons §4 Organization filters; impl-customer-service §4); services still check the organization themselves. Root entry is a navigation grant, not authority to read or change every case, order, return or financial record. `mantle.party.PartyServices.setup#UserOrganizationInfo` supplies the same organization context as the existing roots. The root requires an organization; the UI displays it and preserves it through every shared-screen link.

The menu, to depth two, with the screen each entry opens. Detail screens are reached from records, not permanent menu entries.

- Home → Home
- Cases → Cases (`CustomerService/Cases/Cases`); Channels → ChannelSessions
- Customers → Customers
- Orders → Orders (`CustomerService/Orders/Orders`); Change requests → OrderChanges
- Returns → Returns (`CustomerService/Returns/Returns`); Warranty → WarrantyClaims
- Approvals → Approvals (M, R)
- Availability → InventoryAvailability, StockAtDate (the Warehouse report, mounted), Product360
- Knowledge → Knowledge; Article feedback → ArticleFeedback
- Reports → Reports, with SLA compliance → ServiceLevelCompliance, Response times → ResponseTimes, Case volumes → CaseVolumes, CSAT results → SatisfactionResults and Return analysis → ReturnAnalysis; CaseAnalytics opens from a case
- Settings → Settings, a settings landing that links Queues, AgentTeams, AssignmentRules, SLA policies → ServiceLevelPolicies, StatusCategories, CaseTypes, CaseTemplates, SavedReplies, ChannelRouting, ReturnPolicies, KnowledgeSources, FeedbackForms, ServiceDefaults and ChannelAutomation (later)
- Support, the PASS app of §8 (`screen/Support.xml` in mr-pass, the `support` mount; not part of this menu): SupportHome, MyCases, MyReturns

Cases, Orders, Returns and Availability are menu groups, so their lists sit inside them (`CustomerService/Cases/Cases`), as Warehouse does with `Warehouse/Returns/Returns`. Availability matches the existing placeholder `screen/CustomerService/Availability.xml`. Cases defaults to Assigned to me; managers can choose New/unassigned as their personal default. Home is the root landing. Depth remains two; long settings lists use a settings landing and links.

Home, the landing, shows these panels, each only to the roles named:

- a KPI strip (all roles): open, overdue, unassigned, SLA compliance, first response, resolution and CSAT, each with its period, denominator, timestamp and the change against the previous period of the same length;
- My cases (A, M, D);
- Team queues (A, M);
- Returns awaiting approval (R, M);
- Approvals waiting (M, R);
- shortcuts: New case and Request return.

Role shorthand used below: **A** service agent; **M** service manager; **D** order-desk operator; **R** return authorizer; **W** stock/quality capability; **F** financial settlement capability; **K** knowledge author; **S** service administrator; **C** customer contact. These are proposed capability bundles over existing users, groups and organization membership, not separate agent accounts. Sensitive capabilities include `case.manageTeam`, `case.merge`, `order.change.approve`, `order.change.apply`, `return.authorize`, `stock.receive`, `quality.dispose`, `invoice.credit`, `payment.refund`, `case.feedback.read` and `service.configure`; services check the underlying record and organization as well as the action. Read-only tabs do not imply mutation rights. Customer membership and contact access are checked server-side for every result and action, including searches and attachments.

**Capability groups.** The letters map to the user groups of the crosscut §1 capability table (D22), so a standalone service business can configure them. A is proposed `BOSS_CUSTOMER_SERVICE_AGENT`, M `BOSS_CUSTOMER_SERVICE_MANAGER`, D `BOSS_CUSTOMER_SERVICE_ORDER_DESK`, R `BOSS_CUSTOMER_SERVICE_RETURN_AUTHORIZER`, K `BOSS_CUSTOMER_SERVICE_KNOWLEDGE` and S `BOSS_CUSTOMER_SERVICE_ADMIN`; each also grants the root `BOSS_CUSTOMER_SERVICE`. W is Warehouse's receive and inspect grants, plus its quality-manager grant to dispose. F is Accounting's `BOSS_ACCOUNTING_AR` to credit and `BOSS_ACCOUNTING_TREASURY` to refund a payment; a credit without receipt also needs `BOSS_ACCOUNTING_APPROVE`. C is a PASS public account with no UserGroup, which reaches a customer's records only through Mantle's checks of the contact's customer relationship and of `ExternalAccessCapability` (§8). The dotted names above are the actions the services check; each is granted through one of these groups.

**Shell providers.** Register New case and Request return in Quick create; permitted cases, customers, orders and RMAs in the command palette; own due/overdue cases in Today; approvals in the existing Commons Approvals center, mounted here as Approvals; notifications for assignment, SLA warning/breach, customer reply, return decision and feedback. Use the existing Assist context, Chatter, files, presence, preferences and key-map conventions. Providers return the permitted record URL, not an app-root permission shortcut. A new case from an order, chat or message preserves a `RequestRecord` link and the original communication reference.

**Stack contributions (Nov 1, 2026; review L1, L6, L8; crosscut §1.5).** Assist gets case-reply
and case-summary procedure skills (CX-ASSIST). Comms gets a create-case action from a mail, chat
message or voicemail, and `call-context` answers with the caller's open cases; mail intake stays the
existing `createRequest` action. A shipped service dataset with an SLA-breach alert template
(CX-OPS-REPORTS) joins the §7 reports; its clocks and breaches datasets are scoped by Mantle's organization row filter on
the clock's organization, admitted by Insights (impl-insights P3, owner contract) and read by Customer Service's managers and
administrators and the Insights groups, each their own organizations' clocks. There is no Sync or device contribution (CS-STACK).

**Interaction contract.** XML forms are the default. Saved finds, select-columns, date-periods, accessible statuses and list/board switching follow the style guide. Every board move has an equivalent row action and confirms the same transition; bulk operations report success or a named failure per case, preserving successful independent items. Browser keyboard shortcuts supplement visible controls. Terminal users get searchable lists, numbered actions, plain-text conversation and explicit confirmations; they never need drag/drop, hover or rich-text composition. Phone layouts stack the case sidebar beneath facts and retain an explicit Send button. Stock receipt and quality actions mount the Warehouse handheld forms, with scan/manual-entry equivalence and no offline posting.

**Current-source boundary.** The active Shared RequestDetail, RequestRecord and WorkEffortRecord links, email/public intake, Chatter, client audience isolation and working-hours calendars were added after parts of the research. They are reused. The case queue/SLA policy, service-specific authorization, merge/split, saved reply actions, return policy, controlled order-change and feedback association described here are proposed. Existing `ReqDraft`, `ReqSubmitted`, `ReqReviewed`, `ReqInProgress`, `ReqCompleted`, `ReqCancelled` remain valid; `ReqWaitingCustomer` and `ReqOnHold` below are proposed seeds, not current statuses. The inventory service can report that its projection is not ready; the UI must not turn an unavailable projection into zero availability or a promise.

**Shared record rules** (impl-drawers-commons §4; impl-customer-service §4). A case's organization is a RequestParty in the OrgInternal role, and its customer, contact and assignee are RequestParty rows in the Customer, Reporter and Assignee roles; a team member is a dated PartyRelationship from the agent to the team; a queue's organization is a proposed owner field on RequestCategory; a return's assignee is a dated ReturnParty row. Policies, settings, mappings and rules change by effective-dated rows with their key fields audit-logged, not by versions: a draft is a row with no from date, Publish starts it from a date and ends the row it replaces, and a case, episode, return or invitation keeps the row it was evaluated against and the time. Case templates and feedback forms are DbForms whose fields, options and dependency rows are effective-dated with audit-logged key fields, read as of a response's time (§9). Records of their own stay only where a fact has its own identity: the SLA episode and its events, a case relation, the order-change, warranty and return authorization decisions, article feedback, the feedback invitation and the assignment cursor. Every authorization, application, decision, settlement call, bulk action, saved-reply apply, send and Support submission names its source revision and an operation key on Accounting's CX-POSTING operation record (impl-accounting §4).

**Existing automation.** Several Mantle service ECA rules and one entity ECA rule already run on the paths designed here: order approval, reservation and the order emails, the return approval and receipt rules, the sales invoice at pack, the reservation of released stock, the invoice email at finalize and the request triage notice. §13 Decided lists each one and says whether this design keeps it, runs it under a condition or replaces it, for the crosscut §1.3 register (D1). Each Mantle rule change keeps Mantle's default behind its own flag, off by default: the return and pack-invoice rules are Accounting's flags on `PartyAcctgPreference`, and Customer Service's own are ServicePolicy flags (impl-accounting §4).

## 2. Screens

All internal paths are under `CustomerService/`. `Support/` paths are pages of the proposed PASS app Support (`screen/Support.xml` in mr-pass, the `support` mount), outside BOSS (§8; impl-customer-service §4). A Support page cannot mount a BOSS screen, since BOSS is not a PASS dependency: its Reused cell names the BOSS screen or crosscut row it follows, and it calls Mantle's services through PASS's facade. Scope uses the guide's definitions: `parity` replaces something MarbleERP or SimpleScreens has, `new` has no baseline, and `later` is designed but built after the first release. A `parity` screen may still gain new service behavior, which its section describes. Shared rows reference their single definition; detail sections provide context only. Public pages use PASS's public accounts and request contract over Mantle's external-access checks and need no BOSS grant.

## 3. Cases

### Home

**Layout.** KPI strip above My cases, Team queues and Returns awaiting approval. Counts use the same access filter and saved-find definitions as Cases/Returns. Open, overdue, unassigned, SLA compliance, first response, resolution and CSAT show period, denominator and timestamp; absent SLA/feedback data is “Not configured”/“No responses”, never zero performance. Each panel shows only to the roles §1 names for it, so a K, S, F or W user lands on the KPI strip and the shortcuts their grants allow, not on a page they cannot use. Each KPI shows its change against the previous period of the same length, and a user who may see both splits My figures from Team figures (Frappe's "My Stats" and "My Organization").

Otherwise the customer sees "Cancellation requested", and an agent decides.

**Kinds applied here (D9).** Customer Service applies only two kinds of approved change. The cancel kind cancels the open remainder of a line: `apply#OrderChange` calls `mantle.order.OrderServices.cancel#OrderItem` with cancelQuantity, whose rule re-reserves the line's remainder, so no `reduce#AssetReservation` follows (it would under-reserve; impl-customer-service F66). The substitution kind answers a short pick: Warehouse records the short pick, `apply#OrderChange` adds the approved substitute line and cancels the short remainder, and Warehouse picks the substitute. Substitute candidates are the product's `PatEquivalent` and `PatReplacement` associations, which Products maintains on Product360. Every other kind (price, quantity increase, ship date, address, ship method, carrier) is filed here as a proposal and routed to the order owner, Sales ([Sales §6](design-sales.md#6-orders-and-commercial-changes)), which decides it and applies it through the shared OrderDetail guard. Customer Service never applies those kinds itself. `decide#OrderChange` and `apply#OrderChange` check the permission of the change's kind: `ORDER_CHANGE_APPROVE` and `ORDER_CHANGE_APPLY` for cancel and substitute, Sales' `SALES_APPROVE` and `SALES_ORDER_CHANGE` for the commercial kinds.

Apply locks the source order and relevant allocations; validates approval, revision, current stock, shipped/billed/paid quantities, pricing version and permissions again. The lock is `OrderHold` with an `OrderHoldReason` of type Change (OhtChange), placed through `hold#Order` and released through `release#OrderHold`, which returns it to its pre-hold status when no other reason is open (D7). Apply never uses `OrderBeingChanged`, which Mantle refuses from Placed, Approved or Sent. A shipped item, with its invoice finalized at ship, is `AlreadyShipped` and becomes a return/replacement and its credit memo (below), and posted entries never disappear. Cancellation releases only eligible reservations/demand; it leaves fulfillment and financial reversals as explicit related work. Substitution requires compatible product/unit and customer consent and reruns pricing/availability. Closed financial period returns `ClosedPeriod`, not silent backdating. Failures `StaleOrder`, `StockChanged`, `AlreadyShipped`, `BillingConflict`, `ApprovalExpired`, `Forbidden`, `ClosedPeriod` leave the order unchanged. A separate notification failure leaves Applied with delivery pending, not a second application. Terminal uses the same before/after table and confirmation.

**Receiving sides.** On apply, Warehouse re-validates the open picks of each changed or cancelled line and releases its reservations through `mantle.product.AssetServices.remove#OrderItemReservations` or `reduce#AssetReservation`; a pick in progress returns `StockChanged`. Between pack and ship the sales invoice already exists in process: behind Accounting's D3 flag the kept `ShipmentOutgoingPackedCreateInvoices` rule makes it at pack as InvoiceInProcess, without applying payments, and a ship rule finalizes it, posting it, applying captured payments and sending it (impl-accounting §4). Card payment is captured. So the change follows the path Warehouse built: the package is reopened through `mantle.shipment.WarehouseTaskServices.reopen#ShipmentPackage`, which releases the shipment's lines from the in-process invoice through `mantle.account.InvoiceServices.release#ShipmentInvoiceLines`, without the RECEIVABLE_EDIT check of `release#ShipmentDraftInvoice` (impl-warehouse F275); the line is reduced through `cancel#OrderItem`, which sets `ShipmentItemSource.putBackQuantity`; and the stock is put back through `reverse#Pick`. Apply does the reopen itself under `ORDER_CHANGE_APPLY` (Nov 1, 2026): the order desk holds no `SHIPMENT_PACK`, so apply calls the reopen's work without its `SHIPMENT_PACK` and user-facility checks, as the reopen calls `release#ShipmentInvoiceLines` without RECEIVABLE_EDIT; apply has checked the change and the order's organization, and the reopen keeps its state, confirmation and reason checks. Apply never calls `release#ShipmentDraftInvoice` or `mantle.account.PaymentServices.refund#OrderPayment`, which need the RECEIVABLE_EDIT and PAYMENT_EDIT the order desk lacks; a refund of a captured payment stays an F action. After ship the change is `AlreadyShipped`, and a return and its credit memo handle it.

**Source.** Research §6/13; active OrderEntities/OrderServices; [R4](#reference-files). **Needs.** CS-ORDER-CHANGE, CS-FORM-ELEMENTS, CX-ORDER-CHANGE, CX-PRICING, CX-AVAILABILITY, CX-POSTING, CX-ACCESS.

## 9. Settings

Settings use XML forms, permission-filtered lists and explicit Save/Preview/Publish actions. Browser reordering always has sequence fields/Move up/down for terminal and keyboard users. Policies, settings, mappings and rules are effective-dated rows with their key fields audit-logged, not versions (§1 Shared record rules): a draft is a row with no from date, Publish starts it from a date and ends the row it replaces, nothing is overwritten or deleted, and a case, episode, return or invitation keeps the row it was evaluated against and the time. Case templates and feedback forms are DbForms whose fields, options and dependency rows follow the same rule: a draft field has no from date and Publish starts it; an answered field or option is ended, never deleted; label, required and option edits are audit-logged; a field whose type or meaning changes, or a change set for a later date, is a successor field from that date. A FormResponse reads its form as of its response time, so earlier answers stay readable as submitted; no DbForm is cloned for a version. No administrator-entered JavaScript executes in a customer's case form.

### End-to-end review cases

| Scenario | Required outcome and failure behavior |
| --- | --- |
| Product/variant → supplier price → requisition/RFQ → PO → partial receipt/inspection → bill match/payment | Service sees only customer-safe Product/availability facts. Incoming dates remain qualified; failed inspection holds stock, not a fulfilled promise. PO/receipt/match/payment are read via permitted source links, with Purchasing/Warehouse/Accounting ownership. |
| Shortage → buy/make/transfer → issue → partial completion → finished stock/valuation | Availability exposes distinct plan/supply provenance; no case/agent creates a duplicate replenishment demand. Released-BOM changes are Manufacturing replan/reapproval events; customer promise updates derive from changed supply readiness. Only accepted finished stock increases usable supply; Accounting WIP/valuation remains separate. |
| Order → reservation → pick shortfall → packing/shipping → invoice/payment | Starts from a placed sales order (Sales pass or import). Warehouse records the short pick; service sees the shortfall, proposes a substitute, captures consent and applies it through OrderChangeDetail's substitution kind; Warehouse picks the approved substitute (D9). Between pack and ship, the change first reopens the package, which releases the in-process invoice; after ship the change is AlreadyShipped and goes to a return. Concurrent fulfillment returns StaleOrder/AlreadyShipped; substitution rechecks units/price/tax/stock and does not delete existing issued/billed history. |
| Case → RMA → partial receipt → failed inspection/disposition → credit/refund | R authorizes with no settlement at approval, W receives through `receive#ReturnItems` and holds/disposes, F settles permitted quantity/amount through `settle#Return`; partial credit and retries cannot exceed cumulative source eligibility. Receiptless credit is an explicit exception with no stock. Case resolution cannot complete return settlement. Supplier recovery is a separately linked supplier return. |
| Physical count → intervening stock movement → variance review → posting/retry | Service does not post counts; availability as-of and current promise are revalidated after Warehouse posts the movement-aware variance. A stale count cannot be used to promise stock. Posting retry returns the original result; case follow-up message may retry independently. |
| Case intake → assignment → pause/reopen → resolution → CSAT | Existing intake routes to category/team, records original receipt, deterministic assignment uses schedule, customer wait pauses only configured clock; first response never restarts. Linked work completion prompts agent. Reopen creates resolution episode with prior breach retained; one scoped feedback invitation per eligible episode, duplicate POST returns prior response. |
| Unauthorized actions, cancellations, closed period and standalone use | Context never grants access. Unapplied order changes and unreceived returns may cancel by policy; posted effects require explicit reversals. ClosedPeriod prevents financial posting and leaves source/audit intact. Standalone A+W/F invokes common services without unrelated app-root grants. |
| Independent failures | Batch results name each accessible case/return/document and outcome; continue other independent items. One merge, source return credit, reservation/application or stock/financial posting is atomic. External send/refund/label uncertainty is durable Pending and reconciled by operation key. |
