# Attack surface: staff applications (mr-boss and Mantle)

The staff applications: mr-boss and the Mantle (mr-mantle) services it reaches. The framework's administration services that BOSS Admin shows are in [Attack-Surface-Admin.md](https://github.com/moqui/mr-moqui/blob/master/docs/security/Attack-Surface-Admin.md). The token routes mr-boss adds (`/s`, `/u`, `/cal`, `/r`, `/i`) and its rate limits are under [Token routes](https://github.com/moqui/mr-moqui/blob/master/docs/security/Attack-Surface-Routes.md#token-routes). The public applications are in [Attack-Surface-Apps-PASS.md](https://github.com/moqui/mr-pass/blob/master/docs/security/Attack-Surface-Apps-PASS.md). This is one file of the attack surface map. The index, how to read a row, the defaults and the lock-down advice are in [Attack-Surface.md](https://github.com/moqui/mr-moqui/blob/master/docs/security/Attack-Surface.md).

## Access model

mr-boss's `MoquiConf.xml` mounts sixteen app roots under `component://webroot/screen/webroot/apps.xml`, each at `/qapps/<App>`: Commons, Comms, Sales, Marketing, CustomerService, Commerce, Products, Purchasing, Warehouse, Manufacturing, Maintenance, Accounting, People, Projects, Insights and Admin. The file names no property that turns an app off; an app is mounted when the component is loaded. The framework's `BasicComms` item is set `menu-include="false"` there and stays mounted. The same file adds the five token routes ([Token-route screens](#token-route-screens)), two rate limits, and three privileged groups (`BOSS_ADMIN_ACCESS`, `BOSS_ADMIN_BACKUP`, `BOSS_ADMIN_ADMIN`) to the framework's `privileged-group` list.

The grants are seed data: `mr-boss/data/BossSetupData.xml` (`type="seed-initial"`, 448 authorization rows, 119 capability bundles), `BossAccountingSetupData.xml`, `BossSetupSalesData.xml`, `BossSetupMarketingData.xml`, `BossSetupMaintenanceData.xml` and `BossSetupPeopleReportData.xml`. The other four `*ReportData.xml` files (Commerce, Customer Service, Maintenance, Marketing) grant their report documents to `ADMIN` only; the readers are granted the dataset artifacts in the setup files ([Row isolation](#row-isolation)). The rows follow one pattern.

- **App root.** An artifact group holds the root screen (`component://mr-boss/screen/<App>.xml`) with `inheritAuthz="Y"`. A launcher group gets `AUTHZT_ALLOW` on it: `BOSS_USERS` for Commons and Comms, `BOSS_PEOPLE` for People, `BOSS_ACCOUNTING` for Accounting, `BOSS_PROJECT_TEAM` and `BOSS_PROJECT_CLIENT` for Projects. The seed describes `BOSS_ADMIN`, `BOSS_WAREHOUSE`, `BOSS_PURCHASING`, `BOSS_MANUFACTURING` and `BOSS_CUSTOMER_SERVICE` as launcher groups too. The app's administrator group (`BOSS_<APP>_ADMIN`) and the framework's `ADMIN` group each get `AUTHZT_ALWAYS` on it. `BossSetupData.xml` holds 28 `ADMIN` `AUTHZT_ALWAYS` rows.
- **Sub-area.** An artifact group holds an area's screen with `inheritAuthz="Y"`, an `AUTHZT_DENY` row for the launcher group and an `AUTHZT_ALWAYS` row for each role group that works there (for example `BOSS_PPL_PAYROLL`: `People/Payroll.xml`, DENY for `BOSS_PEOPLE`, ALWAYS for `BOSS_PEOPLE_PAYROLL` and `BOSS_PEOPLE_PAYROLL_APPROVE`).
- **Single artifacts.** A group without the launcher gets a non-inheritable ALLOW on named screens, transitions and services (`BOSS_PPL_SELF`, `BOSS_PPL_PAYSLIP_SELF`, `BOSS_PPL_KIOSK`, `BOSS_ADM_SETTINGS_INDEX`; for `BOSS_PEOPLE_SELF` also `PeopleMyInterview` and four recruiting services, `BossSetupData.xml:5479-5491`, the clock and PIN, `:5678-5689`, own balances and requests, `:5626-5633`, and own shifts, `:5699-5705`).
- **Self-service areas.** `BOSS_PEOPLE_SELF` also holds inheritable ALLOW rows on whole areas, so every screen, transition and service below them is open to an employee without the People launcher, each service checking itself: `People/Time.xml` (`BOSS_PPL_TIME_SELF`, `BossSetupData.xml:5527-5533`), `People/Expenses.xml` (`:5718-5724`), `People/Development.xml` (`:5744-5750`), `People/Performance.xml` (`:5851-5857`), `People/Employees/Grievances.xml`, `Shared/RequestDetail.xml` and `Shared/Chatter.xml` (`BOSS_PPL_CASES_SELF`, `:5832-5840`), and `Shared/RecordFiles.xml` (`BOSS_PPL_FILES_SELF`, `:5778-5784`). The artifact is the screen file, and authorization is required only on the last screen of a path (`crates/moqui-core/src/screen/render.rs:1697`, `:1712`), so a grant on a shared panel opens it at every mount: `Chatter` and `RecordFiles` under all sixteen roots, and `RequestDetail` at its eleven mounts with the transitions it includes from Warehouse, Purchasing, Customer Service, Maintenance, Commerce and Sales (`Shared/RequestDetail.xml:90-143`). A self-service employee opens them under any root whose always-actions call only `anonymous-view` or granted services: Products, Projects, People, Admin, Commons and Comms. The seed's comment (`:5825-5831`) rests this on the panels deciding by record.
- **Services by pattern.** Some roots also name services as artifacts with `inheritAuthz="Y"` (`ironstone\.people\..*` on `BOSS_PEOPLE`; `ironstone\.accounting\..*` and eight `mantle.ledger` service files on `BOSS_ACCOUNTING_ACCESS`).

`BOSS_USERS` opens the Commons and Comms roots, Admin's `Admin/Settings/SettingsHome.xml` and `ironstone.admin.ContextServices.get#SharedContext` (both non-inheritable), and is a member of the `BOSS_RECORDS` drive. In `BossSetupData.xml` one row names `ALL_USERS`: `BOSS_PPL_ACCESS_REQUEST_ALL`, an ALLOW on the services `ironstone.admin.LifecycleServices.request#Provisioning` and `request#AccessEnd`, with the filter sets `MANTLE_USER_ORG` and `MANTLE_PRIVATE_CONTACT` (`:5463-5465`, SEC-BOS-104).

**The rule** (`crates/moqui-core/src/user/authz.rs`, `is_permitted`). The steps run in this order.

1. When the frame above holds an inheritable `AUTHZT_ALWAYS` for the action, the artifact is permitted and no record is read.
2. Otherwise the user's records for the artifact are read. An `AUTHZT_ALWAYS` record permits at once, whatever DENY record also matches. An `AUTHZT_DENY` record refuses once every record is read. An `AUTHZT_ALLOW` record counts only when no DENY record matched and no frame above was denied. A record whose condition fails to evaluate applies when it is a DENY and does not apply otherwise.
3. With no matching record, an inheritable grant of the frame above permits the artifact when it is not a DENY, is for the same user and covers the action.

An inheritable ALLOW on an app root therefore permits every screen, transition, service and entity operation called below the root, except an artifact that a DENY record names for one of the user's groups. A service called below a root is gated by the checks in its own body (`ec.user.hasPermission`, the scope libraries such as `AccountingPolicy.js` and `SalesAccess.js`), not by an authorization record. A user in both a launcher group and a role group passes a sub-area through the role group's ALWAYS.

**Screen extensions.** `mr-boss/screen-extend/basic-comms/screen/BasicComms/` extends eight framework screens (`Home`, `Chat`, `Calls/Call`, `Calls/Voicemail`, `Inbox/Mail` with eleven transitions, `Inbox/Compose`, `Inbox/MessageDetail`, `Settings/Index`), and `screen-extend/webroot/.../apps/AppList.xml` extends the launcher. The extensions call `ironstone.customerservice.ChannelServices.create#CaseFromMessage`, `ironstone.sales.ContextServices.create#LeadFromMessage` and `ironstone.shared.ChatterServices.search#Users`. They run under the authorization of the screen they extend.

**Comms.** basic-comms `InboxServices.run#Operation` passes the request's parameters to IronStone's `get#InboxSource` (`mr-boss/service/ironstone/comms/InboxServices.xml:1146-1200`), which runs 24 `ironstone.comms` services by name (`:1181-1189`). Whom a Comms user reaches is Mantle's `party/PartyReach.js` `visibleParties` (wrapped by `mantle.party.PartyServices.filter#VisibleParties`): each party read with authorization on under the caller's entity filters, not another user's personal contact, and a person who works for an internal organization (or a unit whose `PrtOrgRollup` root is internal) only when one of those organizations is one the user may see or shares its top-level organization with one the user works for; another top-level organization's staff whose party is shared (`_NA_`) are not reached. The contact-card hook (`get#ContactCardProvider`, `get#ContactCard`, `:1075-1153`) is reached by basic-comms `Inbox/Mail.xml:101-104` (`contactCard`, a GET with `partyId` from the request) and runs as the Comms app (`crates/moqui-core/src/service/shell.rs:173-175`); it names a party, found by `partyId` or matched by address, only when `visibleParties` answers it, and reads its organization under the Comms filters; otherwise the card is the address and name alone (SEC-BOS-100). In `comms/ComposeServices.xml`, `search#Recipients`, `get#CallContext`, `get#CallTarget` and `get#RecipientSource` read parties with authorization on under the Comms filters, and all but `get#CallContext` keep only those `visibleParties` answers; the email search finds user accounts in the query (`PersonWithUserAccount` with authorization on, a page at a time) and offers one only when `visibleParties` answers its party and the `chat-target` providers do not refuse it (`:444-470`, SEC-BOS-99). A `party:` recipient chip, an address chip and a contact group's members are resolved by the same rule (`resolve#Recipients`, `:701-832`), as is the composer's reply-all (`send#Compose`), and `create#Message` (mr-mantle `party/CommunicationServices.xml`) refuses any other recipient of an internal Message, a reply keeping the thread's existing participants (SEC-BOS-98). `match#Addresses` (`InboxServices.xml:278-324`) reads a party by email address only when `visibleParties` answers it, a directory by address by its description. A message attachment is sent only for a message `get#Thread` or `get#InternalThread` shows (`:567-589`). Comms' own screens are `screen/Comms/Moderation/*` over `mantle.forum.ModerationServices` and `screen/Comms/Consent/*` over `ConsentServices.xml` (a Marketing consent editor is scoped to its organizations' lists and contacts, `:34-80`). Who: any `BOSS_USERS` member.

**Demo data.** The files `mr-boss/data/*DemoData.xml` are `type="demo"`. `BossUsersDemoData.xml` holds 144 `currentPassword` attributes and `BossAccountingUsersDemoData.xml` holds 11; the rows read carry the same `SHA` hash value. Twenty-one `*DemoServices.xml` files hold 47 services with `authenticate="anonymous-all"`. No file under `mr-boss/screen`, `mr-boss/screen-extend` or `mr-mantle/service/*.rest.xml` names a `DemoServices` service. The demo data files call them as elements (`<ironstone.commons.DemoServices.load-CommonsDemo/>`), so they run when the `demo` data type is loaded. `BossDemoData.xml` also names `ironstone.commons.DemoServices.approve#DemoPurchase` and `refuse#DemoPurchase` as the services of a demo approval topic. `BossZPortalDemoData.xml` (`type="demo"`) calls `ironstone/accounting/Demo.js` `load#PortalDemo`, which creates an invoice pay link and a purchase order bill-upload link (`ExternalAccessCapability`, 366 days) whose tokens are constants (`Demo.js:1625-1628`, `:1746-1763`), and two PASS accounts with the demo password's hash (`:1772-1800`). The default first load is `seed,seed-initial,install` (`MoquiDefaultConf.xml:275`); the dev and demo confs and `./moq load` load `all` (`runtime/conf/MoquiDevConf.xml:14`, `MoquiDemoConf.xml:10`, `scripts/moq/run.sh:56-57`). Nothing refuses the `demo` type on a production instance; that rests on the deployment checklist (`docs/Run-Deploy.md:217`).

## Row isolation

Five entity filter sets hang on the authorization rows. How a filter set is evaluated is in [Entity authorization and row filters](https://github.com/moqui/mr-moqui/blob/master/docs/security/Attack-Surface-Data.md#entity-authorization-and-row-filters).

| Set | Defined in | Applies when | Filters |
|---|---|---|---|
| `MANTLE_USER_ORG` | `mr-mantle/data/10-seed/01OrganizationFilterSets.xml` | always (no `applyCond`) | By `filterOrgIds`: `Invoice`, `Payment`, `OrderPart`, `ReturnHeader`, `Shipment` (either party), `FinancialAccount`, `AcctgTrans`, `TimePeriod`, `Party`, `Product`, `ProductCategory`, `ProductFeature`, `ProductFeatureGroup`, `ProductStore`, `Facility`, `UserAccountOrganization`, `InternalOrganization`, `SalesOpportunity`, `SalesForecast`, `Agreement`, `MarketingCampaign`, `MarketSegment`, `ContactList`. The `PartyRelationship` filter is inside a comment (see `15-seed-initial/OrganizationFilters.xml`) and does not apply. |
| `MANTLE_ACTIVE_ORG` | `mr-mantle/data/10-seed/01OrganizationFilterSets.xml` | `applyCond="activeOrgId"`; `allowMissingAlias="Y"` | The same entities by `activeOrgId`. |
| `MANTLE_PRIVATE_CONTACT` | `mr-mantle/data/15-seed-initial/OrganizationFilters.xml` | always; `allowMissingAlias="N"` | `mantle.party.Party`: `privateOwnerUserId` is null or the user's id. A find on a view over `Party` with no alias of `privateOwnerUserId` is refused; every view over `Party` aliases it, one alias for each `Party` member (SEC-DAT-11). |
| `COMMERCE_STORE` | `BossSetupData.xml:2318` | `applyCond="ec.user.context.commerceStoreIds != null"`; `allowMissingAlias="Y"` | `mantle.product.store.ProductStore` by `productStoreId`. |
| `BOSS_PROJECT_CLIENT` | `BossSetupData.xml:376` | always; `allowMissingAlias="N"` | `WorkEffort`, `WorkEffortParty`, `Request`, `CommunicationEvent` and further entities, by the lists `clientProjectIds`, `clientPartyIds`, `clientContactPartyIds` and `clientStatusUpdateIds` of the user context, each `['_NA_']` when unset. |

The two organization sets name no `mantle.humanres.*`, `mantle.work.*`, `mantle.request.*` or `mantle.account.method.*` entity, no order header and no ledger entry, and no `moqui.security.UserAccount` (only `UserAccountOrganization`). Rows of those entities are limited to an organization only by service code. `PartyContactMech` is filtered by no set: `PartyContactMechInfo`, a view over `PartyContactMech` and `ContactMech` with no `Party` member, is reached by neither the organization sets nor `MANTLE_PRIVATE_CONTACT` (`mr-mantle/entity/PartyViewEntities.xml:437-443`), so a service that reads a party's addresses through it (`mantle.party.ContactServices.get#PrimaryEmailAddress`) answers them for any party id.

**Which rows carry which set.** A launcher ALLOW row carries `MANTLE_USER_ORG` and `MANTLE_PRIVATE_CONTACT`. The `ADMIN` and `BOSS_<APP>_ADMIN` ALWAYS rows on a root carry `MANTLE_ACTIVE_ORG` and `MANTLE_PRIVATE_CONTACT`; `BOSS_PROJECTS_MANAGER` carries `MANTLE_USER_ORG`. With no active organization selected, `MANTLE_ACTIVE_ORG` does not apply, and an administrator's finds are not limited by organization. `COMMERCE_STORE` is attached by `ArtifactAuthzFilter` rows to 22 Commerce rows (`BossSetupData.xml:2323-2344`, among them `BOSS_COMMERCE_ADMIN`, `BOSS_COMMERCE_APPADMIN`, `BOSS_COMMERCE_ROOT` and the `BOSS_COM_WEBSITE_*` rows); the other three of the file's 25 `ArtifactAuthzFilter` rows are `BOSS_SALES_CALC_PROFILE`'s (`:148-150`). `BossAccountingSetupData.xml` holds no `ArtifactAuthzFilter` row: every authorization row nests its `filters`, the launcher and role rows `MANTLE_USER_ORG` and `MANTLE_PRIVATE_CONTACT`, the `BOSS_ACCOUNTING_ADMIN` rows `MANTLE_ACTIVE_ORG` and `MANTLE_PRIVATE_CONTACT` (`:194-561`), so with no active organization an Accounting administrator's finds under Accounting are not limited by organization. `BOSS_PROJECT_CLIENT` is on the client group's ALLOW on the Projects root, in place of the organization set. Every role group's `AUTHZT_ALWAYS` row on a BOSS screen artifact group below a root (137 of them: Accounting's areas and quick creates, People's Payroll, Time, Development and Reports, Products' Prices and Settings, the shared price, cost and valuation screens and others), and the two on the Products import services, carries the root's `MANTLE_USER_ORG` and `MANTLE_PRIVATE_CONTACT`, so a role user's direct finds under an area are filtered (`AppOrganizationFilters.spec.js` checks every such row; plans/Security-Review.md SEC-BOS-01, fixed). The 47 ALWAYS rows without them are on no screen: the Insights report-engine service and `/moqui/reports` REST groups (the report engine applies its own `MantleOrganization` row filter), rows with no artifacts and the demo delegate row.

**Which record supplies the filters.** `crates/moqui-core/src/user/filter.rs` (`applicable_filters`) takes the filter sets of one record: the record that authorized the frame on top of the artifact stack. A sub-area ALWAYS row becomes that record for the area's screen, and by step 1 of the rule for everything called below it; those rows carry the root's sets (for example `BOSS_ACCT_Receivables_AR`, `BossAccountingSetupData.xml:225-227`; `BOSS_PPL_PAYROLL_OPERATOR`, `BOSS_PPL_PAYROLL_APPROVER` and `BOSS_PPL_HR_AREA_HR`, `BossSetupData.xml:5568-5576`, `:5434-5437`). For a member of `ADMIN` or of the app's administrator group, step 1 keeps the root's ALWAYS record and its filter sets. An ALLOW record that matches a service itself authorizes that service's frame in place of the root's inherited record (`crates/moqui-core/src/user/authz.rs:568-569`), and when several match the last wins (`:554`). Products' `BOSS_PRODUCTS_SERVICES_READ` (`BossSetupData.xml:294-307`, `BOSS_PRODUCTS` on `ironstone\.products\..*`, `mantle.product.ProductImportServices`, `CatalogRecordServices`, `CatalogCheckServices`, `PriceServices.get#EffectivePriceList` and `ironstone.commons.PaletteServices.get#RecordLink`, `inheritAuthz="Y"`) carries the root's `MANTLE_USER_ORG` and `MANTLE_PRIVATE_CONTACT`, so finds inside those services are filtered as the root's are; the services read check owners themselves too (`ironstone/products/Pricing.js:31-33`, `Prices.js:203-210`). So does Insights' `BOSS_INS_REPORT_FLOW_FLOW`, the flow editors' ALWAYS row on the FlowMap writes (`:4776-4778`, SEC-BOS-104).

**Report datasets.** A dataset is authorized by the user's own records (`authz.rs:341-348`, `moqui-report/src/lib.rs:181`), so `/moqui/reports`'s inheritable ALWAYS (`BossSetupData.xml:2575`) does not widen which datasets a group reads, and actions match exactly (`authz.rs:521`). The readers are granted the dataset artifacts in the setup files (`BossSetupData.xml:3381-3462`, `BossSetupSalesData.xml:268-276`, `BossSetupMarketingData.xml:448-458`, `BossSetupMaintenanceData.xml:404-414`), each scoped by its `rowFilterService`: the organization through `get#OrganizationRowFilter`, which refuses another `userId` and ignores an active organization outside the viewer's (`PartyServices.xml:660-679`), and Sales and Marketing by their own scope policies. The Commerce datasets (`BOSS_COM_DATASETS`, `BossSetupData.xml:3448-3455`: checkouts, payment attempts and feed builds) are organization-scoped, not store-scoped: `commerceStoreIds` does not reach the report engine. `BossSetupPeopleReportData.xml` gives the People Reports area ALWAYS rows with both sets to HR, recruiting, development, payroll and payroll approval, and a DENY to `BOSS_PEOPLE` (`:109-133`), and the group `BOSS_PEOPLE_INSIGHTS` ALLOW VIEW on three People datasets with their `DataDocumentUserGroup` rows (`:135-153`; per-person leave and employment rows of the viewer's organizations, restricted qualification kinds left out, `:92-95`). Its `BOSS_INSIGHTS_DATA` row is UPDATE only and so reads no row.

**Finds under Accounting and People.** The screens' own finds under Accounting and People are lookups (enumerations, `Uom`, `Geo`, `TimePeriodType`), names of ids a service returned, counts, and records read by key and passed to a service that checks them (for example `People/Payroll/PayAdjustments.xml:79` then `decide#Adjustment`, `People/Expenses/ExpenseClaims.xml:38`, `Budgets/BudgetDetail.xml:31-42` after `get#BudgetDetail`). Every People record is read through a Mantle service that checks the People scope. The ironstone Accounting modules and the Mantle `account/` and `ledger/` modules read with authorization disabled through `ledger/EntityLib.js` (`:5`, `find = ... .disableAuthz()`) and check the organization themselves through `AccountingPolicy.js`, `InvoiceWorkflowLib.js`, `PaymentWorkflow.js`, `BankReconciliation.js` and `FinancialAccountServices.check#FinancialAccountAccess`, so the sub-area rows' filter sets do not limit them; Accounting's choice sources are listed under [Accounting](#accounting).

**Where the organization context is set.** Each of the sixteen app root screens calls `mantle.party.PartyServices.setup#UserOrganizationInfo` (`authenticate="anonymous-view"`), in `always-actions` in `Commons.xml`; it is also a method of `mr-mantle/service/mantle.rest.xml`. It writes `userOrgIds`, `filterOrgIds` and `activeOrgId` into `ec.user.context` from `get#PartyOrganizationInfo`, for the signed-in user's own party. It takes no request parameter. The active organization is the user preference `ACTIVE_ORGANIZATION`. A value that is not one of the user's organizations is set to null and the preference is cleared, except for a member of `ADMIN` or a holder of `ACCOUNTING_ALL_ORGANIZATIONS`, who may select any party with the role `OrgInternal` (`PartyServices.xml:631`). `filterOrgIds` is the active organization alone when one is set, else every organization of the user (the organizations the party is related to and their direct `PrtOrgRollup` children that are internal). Accounting's `selectOrganization` (`mr-boss/service/ironstone/accounting/Accounting.js`) writes the preference after checking the organization against `policy.access()`. `Commerce.js` `setupStoreScope` writes `commerceStoreIds`: it leaves it unset for a user with no store assignment and for a system administrator, and sets `['_NA_']` when the stores cannot be read. Projects' root calls `mantle.work.ProjectServices.setup#ClientProjectInfo` for the client lists.

**Reads with authorization disabled.** Under `mr-boss/service` the files with the most lines that call `disableAuthz` or set `disable-authz` are `projects/BillingServices.xml` (37), `projects/CodeServices.xml` (37), `comms/InboxServices.xml` (31), `projects/TimeServices.xml` (21), `comms/ComposeServices.xml` (20), `commons/PaletteServices.xml` (20) and `client/ClientServices.xml` (14); Admin's scripts (`Admin.js:18`, `Lifecycle.js:17`, `Registry.js:17`, `Provisioning.js:11`) and the Accounting modules also read through Mantle's `ledger/EntityLib.js`, whose `find`, `one`, `rows` and `call` disable authorization (`:5`, `:45`). What decides the rows, by file:

- Commons (80 lines, 30 of them in the demo loaders, run by data loads only): a `UserAccount` name or existence, the user ids of a record's parties, a work effort's purpose or type, and the caller's own notification rows, each after a drive, event, calendar, page, space, task, request or party check, or on the caller's own `userId`. Not behind a check: `DriveServices.xml:743` lists every `UserGroup` (id and description) to any Commons user (the share dialog); `KnowledgeServices.xml:1673` answers a space's `GitRepository` branch and `remoteUrl` to any viewer of the space; `ContactServices.xml:1289` disables authorization for the whole body of `migrate#NotDuplicateSettings`, named only by the seed load (`BossSetupData.xml:718`). `PaletteServices.xml`'s 20 reads take a record's type, purpose, root or owner to pick a link; the link's screen checks again and no title is answered, but a record's kind shows by its icon, and by `openRecord`'s redirect for any kind but a task, event, request or message, whose Commons or Comms link is given only when `get#RecordLinkInfo` answers the record visible (`:456-461`). `CalendarServices.xml:1102-1147` reads a share by its publish token, then checks the password.
- Projects and the client: `projects/BillingServices.xml` reads after `check#Money` and `get#VisibleProjectInfo` or `get#ProjectAccess`, a client only through `get#ClientInvoices`; the order line search, link and detail (`:1407-1753`) read only order parts whose customer is a client of the project and whose vendor is one of its vendors (`get#ProjectVendors`, [Orders](#projects) below); a rate of no project is read and written only when it is shared or of one of the user's organizations, a shared one changed only by an administrator of every project (`:968-971`, `:1114-1120`, [Rates and time](#projects) below). `projects/CodeServices.xml` reads after `get#GitRepositoryAccess` or a git read that checks it, with linked work efforts filtered by `get#VisibleWorkEfforts`. `projects/TimeServices.xml` reads after `get#TimesheetAccess`, `get#TaskAccess` or `get#ClientProjectInfo`, except `get#TimePeople` (`:693-720`), which adds the request's `partyId` to the options and reads its name. `client/ClientServices.xml` reads after `get#ClientRecordVisibility` and `get#ClientProjectInfo`. `ProjectServices.xml`, `PlanningServices.xml`, `ResourceServices.xml` and `ProjectRequestServices.xml` read flags or names of rows `get#ProjectAccess`, `get#PlanItemAccess` or `get#VisibleProjectInfo` admitted.
- Comms: `comms/InboxServices.xml` and `comms/ComposeServices.xml` read after `get#Thread`, `get#InternalThread`, `get#RecordLinkInfo` or `get#ContactListAccess`; the contact card, the account search, the `party:` chip and `match#Addresses` read with authorization disabled only of a party `PartyReach.js` `visibleParties` answers (its addresses, its employer), under [Comms](#access-model) above.
- Accounting: `accounting/BankServices.xml` reads after `check#BankAccess` or `check#FinancialAccountAccess`, conditioned on the checked organization or account (`:47-55`, `:106-113`, `:155-167`, `:210-219`).
- Admin: each `EntityLib` read is decided by the caller's own groups or a scope check before it.

`shared/ChatterServices.xml` lines 119-136 read the person and employer of an employment, a review and other People records by key with authorization disabled to build a record's title; for People, Sales and Marketing records the host's own access service runs first (for example `check#EmploymentAccess`, `mr-mantle/service/mantle/party/CommunicationServices.xml:2774-2776`).

What the token services do with the caller's input:

- **Shares.** A share token is 32 characters kept as a hash, with revoked and expiry checks (`FileServices.xml:1934-1935`, `:2680-2685`). `open#PublicShare` counts the opening (`openedCount`, `lastOpenedDate`, `:2742-2744`) and the password tries, 10 a link and 30 a requester in ten minutes (`:2726-2733`), and binds its grant to the token and password hashes for an hour (`:2741`); `..` and the trash are refused (`:2772-2779`, `:2835-2843`), and uploads are limited (`:2912-2927`). A passwordless link's list and download skip `open`, so downloads are not counted. A download with no `path`, or a subfolder's, is a folder zip under the `resource-facade/drive-share` limits (SEC-BOS-83, [Files](https://github.com/moqui/mr-moqui/blob/master/docs/security/Attack-Surface-Files.md)): counted against the requester before anything is read, refused past 1 GiB or 20,000 files (32 levels), kept once per link and folder by its files' state and rebuilt only when the folder changes, each build counted against the link and made under a claim, and written by `ec.resource.writeZip` a window at a time into a part file (`crates/moqui-core/src/script/host/files.rs` `write_zip_file`; `FileServices.xml` `download#PublicShare`, `:2807`). No route rate limit names `/s/*`.
- **Unsubscribe links.** Hashed and expiring; lookups are counted, 100 in ten minutes (`ConsentServices.xml:1473-1482`, `:1565-1574`); `apply#UnsubscribePreferences` subscribes again only as this link's undo within a day (`:1611-1617`); the verification link's root ignores a sender's `Host` (`crates/moqui-core/src/web/mod.rs:844-871`).
- **Published calendars.** `get#PublishedCalendar` checks the token format and a current share naming no user, group or party, and has Mantle's `open#PublishedCalendar` check a password once for a grant of an hour, keyed by the share and its password hash, which the page sends instead of the password on its next loads; only a wrong try counts, 10 a link and 30 a requester in ten minutes, past which the answer is "too many tries" with no hash computed, and the share row is held `forUpdate` while one try is checked (`ironstone/commons/CalendarServices.xml:1127-1160`, `mantle/work/CalendarServices.xml:580-620`; SEC-BOS-102). It answers no parties or resources, and takes any `start`..`end`, each recurring series expanded over it. The `publishToken` is stored as the token (`mantle/work/CalendarServices.xml:424`). No screen makes a publish link: `share#Calendar` with `publish` (`:408-428`) has no caller in the screens, and `Settings/Calendars.xml:50` shares with a user only, so a `/cal/<token>` link exists only from a direct service call or a data load.
- **Request forms.** `create#IntakeRequest` limits 30 requests an hour a project and 5 an address, with the route's 5 POSTs a minute a client (`RequestServices.xml:893-912`); a form may ask a CAPTCHA (`form.captcha`, `:952-954`); files follow `form.files`, `maxFiles` (5), `maxMb` (10) and a kind list without HTML, SVG and scripts (`:879`). A project form's token is the `WstIntakeToken` setting, stored as the token (`:723-725`, `:754-755`). For a project's token the service calls `create#ContactRequest` with no filer or customer, which takes the first enabled person who has the typed address and first name, a private contact included, as the request's filer and customer (`:230-250`, `:950-965`), and marks it `senderVerified` N, as a queue form's request is (`Channels.js:764`; SEC-BOS-103): the Commons and Projects request headers say "Sender not verified: the address was typed into a public form", client users never see such a request (the `BOSS_PROJECT_CLIENT_REQ` filter, `get#ClientRecordVisibility`), and a later non-automatic reply from the typed address confirms the sender (`create#RequestFromEmail`, `SupportCases.js` `confirmSender`).

**Where a gateway's credential is kept.** A payment or shipping gateway (`mantle.account.method.PaymentGatewayConfig`, `ShippingGatewayConfig`) names a `SystemMessageRemote`. **Who changes a gateway.** `mantle.account.GatewayConnectionServices` (`mr-mantle/service/mantle/account/GatewayConnections.js`) is the adapter BOSS Admin's Connections screens use, on the framework's `org.moqui.admin.ConfigurationConnections.js`.
